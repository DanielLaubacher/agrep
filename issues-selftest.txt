1. --structural without --lang silently mis-parses real source whenever
   a string/comment literal contains an unbalanced bracket-family
   character, producing wrong multi-line captures instead of an error
   or a missed match

   Docs (--skill, "Generic family (unknown extensions) knows only
   balanced delimiters, which degrades safely on prose") frame the
   generic fallback as a safe degradation. In practice, run against
   real source it silently does the opposite: it invents multi-line
   matches that splice together unrelated statements.

   Repro (this repo's own source):
     agrep -n --structural 'bytes.Index(:[args])' internal/matcher/structural.go
   vs.
     agrep -n --structural 'bytes.Index(:[args])' --lang go internal/matcher/structural.go

   The call site is `i := bytes.Index(rest, []byte(":["))` on line 41 --
   the argument is a Go byte-slice conversion of the string literal
   ":[", which contains a literal '[' character with no matching ']'
   *as a real delimiter* (it's inside a string). Generic mode doesn't
   know about Go strings, so it treats that '[' as a real open-bracket
   needing to balance, and keeps consuming forward across six more
   statements until something happens to close it. JSON captures
   confirm the damage:

     agrep -n --structural 'bytes.Index(:[args])' --json --compact \
       internal/matcher/structural.go
     -> line 41 "captures":{"args":"rest, []byte(\":[\"))\n\t\tif i < 0 {
        \n\t\t\tsegs = append(...)\n\t\t\tbreak\n\t\t}\n\t\tif i > 0 {
        \n\t\t\tsegs = append(segs, segment{lit: rest[:i]})\n\t\t}\n\t\t
        end := bytes.IndexByte(rest[i:], ']'"  <- spans 6 real
        statements, ends mid-expression

   --lang go on the identical file/line captures correctly:
     "captures":{"args":"rest, []byte(\":[\")"}

   Second independent repro, same root cause, different pattern and
   file (internal/output/collapse.go has several raw-string JSON
   fragments containing bare '{' / '['):
     agrep -n --structural 'append(:[a], :[b])' internal/output/collapse.go
     -> 11 "matches" (several are merged/garbled multi-line spans)
     agrep -n --structural 'append(:[a], :[b])' --lang go internal/output/collapse.go
     -> 8 matches, one per real call site, correctly separated
   (see the line-number diff: generic mode's records for lines 88-98
   collapse into fewer, wrong-content matches; --lang go keeps them
   distinct and correctly bounded.)

   This is exactly the class of bug flagged in issues.txt #2 (silent
   wrong output is worse than an error) but on the *generic* path
   rather than a specific --lang parser, and it triggers on completely
   ordinary code (any string argument containing one bracket/brace/
   paren character that isn't balanced by another one in the same
   literal -- extremely common: format strings, delimiter constants,
   this project's own structural-template syntax ":[" and "]"). Since
   --lang is optional and the CLI never warns when it's omitted for a
   recognized extension (cmd/agrep/flags.go and internal/cli/config.go
   have no such check), a user who runs --structural against a .go/.py/
   .js tree without remembering --lang gets confidently wrong,
   unbounded-looking captures with no diagnostic that anything went
   wrong. Given --block, --scope, and --sections all auto-detect the
   language family from the file extension via lang.ByPath, and only
   --structural requires it spelled out via --lang (silently defaulting
   to Generic otherwise), this inconsistency is an easy trap.

   Not proposing a specific fix (that's a design call -- auto-detect
   family from extension for --structural too, unless --lang Generic
   is explicitly requested; or warn once when a recognized extension is
   being searched without --lang) -- just flagging that the current
   default silently produces worse-than-nothing output on completely
   ordinary code, including this project's own source.

2. --rank defs / kind:"definition" only recognizes Go func/type, not
   const/var -- misses real definitions and can pick a worse --outline
   exemplar than the actual declaration

   internal/output/scope.go's isDefLine for lang.Go:
     case lang.Go:
         return hasPrefixWord(trimmed, "func") || hasPrefixWord(trimmed, "type")
   Top-level `const` and `var` declarations never classify as
   definition-shaped, so they never get "kind":"definition" in JSON and
   never count toward --rank defs's "N defs" signal -- even though "where
   is X defined" for a package-level constant or variable is exactly
   the kind of question --rank defs exists to answer per --skill ("--rank
   defs puts files with definition-shaped matches first ... the right
   mode for 'where is X defined'").

   Repro (real declarations in this repo):
     agrep -r --outline --rank defs 'blockMaxBytes' internal/
     -> "4 (0 defs)  internal/output/block.go  // blockMaxBytes caps an
        emitted block; ..."
   blockMaxBytes IS defined in that file (`const blockMaxBytes = 32 *
   1024`, internal/output/block.go:23) but --outline reports 0 defs and
   picks the doc COMMENT above the const as the file's exemplar line --
   the least informative of the four matching lines -- because the
   actual `const` line never qualifies as definition-shaped and so
   never wins the "definition lines win" tiebreak (per --skill's
   --outline description).

   Second repro, same pattern, `var`:
     agrep -r --outline --rank defs 'pageMarker' internal/output/
     -> "4 (0 defs)  internal/output/agent.go  // pageMarker is the
        marker PDF extraction leaves in Markdown: <!-- p.N -->."
   (pageMarker is `var pageMarker = []byte("<!-- p.")`,
   internal/output/agent.go:58 -- again the doc comment wins instead.)

   Not a documented-contract violation (nothing promises const/var
   coverage specifically), but a real coverage gap for a very common
   real-world query shape against Go code, and it actively degrades
   --outline's exemplar quality rather than just leaving a gap silently
   -- worth deciding whether const/var should count for Go (Rust's
   isDefLine already handles a leading "const" as a modifier before
   "fn", so there's precedent for at least distinguishing a real const
   declaration from other lines).

Minor / non-bug observations
-----------------------------
- --get-region ambiguity handling (multiple func: candidates in one
  file, #N disambiguation) verified correct with a synthetic two-
  function-same-name fixture (Go doesn't allow this for real, so this
  repo's own source never exercises it) -- message format, line
  numbers, and #N selection all matched --skill's description exactly.
- --changed-since main / HEAD / a bad ref / a ref with no diff all
  behaved correctly against this repo's real git history: untracked
  new files included, bad ref -> exit 2 with git's own error text,
  no-diff ref -> exit 1 (reasonable "no match" rather than an error).
- --use-index build, warm reuse, and incremental reindex-on-change all
  verified correct against this repo's own tree (stale entry correctly
  triggered "1 read, 18 reused" and found newly-appended content).
- -M truncation on a genuinely long real line (166 bytes,
  internal/output/scope.go:164) verified: plain-text default (75-byte)
  truncation snaps to a word boundary, explicit -M N sets
  "truncated":true in JSON, and span/region stay full-line-accurate
  under truncation exactly as documented -- this was flagged as never
  verified in the prior corpus evaluation; it holds up on real code.
- --block on Go functions with nested braces, raw-string literals
  containing an unbalanced '{' (internal/output/collapse.go's Finish,
  which contains a raw string `{"type":"collapsed","lines":`), and
  --get-region @func: addressing all correctly balance to the true
  closing brace -- --block's atom-awareness (lang.SkipAtom) does NOT
  have the same string-literal blindness bug as --structural's generic
  mode above, because --block always resolves the real language family
  from the file extension (lang.ByPath) rather than defaulting to
  Generic.
- Binary-file handling: walking this repo with -r (including bin/agrep
  itself, an ELF binary) produced no garbage output, no crash, and
  correctly zero-matched/skipped the binary without an error record.
- --watch verified non-hanging/non-crashing under a 2s timeout (blocks
  as designed; killed cleanly).
- -g globs, --with-file/--without-file, --histogram --capture on a
  --structural hole, and -t/-o multi-stage pipelines all behaved
  correctly against real repo content (flag extraction from
  cmd/agrep/flags.go, error-string extraction from fmt.Errorf calls).
- Method receivers and --structural: `func :[name](:[args])` against a
  method like `func (ms *MatchSet) Len() int` captures the receiver
  parens `(ms *MatchSet)` as :[args] and an empty :[name] (the hole
  before the first literal '(' is zero-width since the receiver's '('
  comes immediately after "func "). This is correct, expected
  comby-style template behavior given that literal template text, not
  an agrep defect -- flagging only as a documentation opportunity
  (--skill's --structural section doesn't mention the receiver case,
  and a user's first instinct with a Go method is likely to write the
  same template they'd use for a plain function).
