1. --batch + --max-tokens misreports per-query totals in JSON (contradicts documented contract)

   Docs (agrep --skill) state the --max-tokens summary carries "true totals,
   never just what was shown". Reproduced counter-example:

     printf 'retry\nbackoff\nexponential delay\njittered backoff\n' > probes.txt
     agrep --batch probes.txt --json --compact --max-tokens 1500 -r \
       ./PragProg/release-it-second-edition_P1.0.md

   Final {"type":"summary",...,"queries":[...]} reports:
     retry: 9 lines, backoff: 0 lines

   Same search with no --max-tokens cap reports the true counts:
     retry: 12 lines (1 file), backoff: 2 lines (1 file)

   So under --max-tokens, the per-query numbers in the final summary are the
   SHOWN counts, not the true counts -- the opposite of what's documented.

   Also: a {"type":"budget_summary", shown_lines, shown_files, omitted_lines,
   omitted_files, queries} record is emitted before the final "summary"
   record. This "budget_summary" type is not listed anywhere in the
   documented JSON contract (match/region/context/count/file/outline/
   variant/suggest/suggest_summary/collapsed/error/summary). Its own
   per-query "queries" array is *also* inconsistent with the true totals
   (e.g. it reported backoff: 1 file / 2 lines in one run, matching the true
   total, while the following "summary" record's queries array for the same
   run reported backoff: 0/0 -- the two summary-ish records disagree with
   each other in addition to disagreeing with the docs).

   Repro is fully deterministic (re-run gives identical numbers).

2. --structural --lang py silently false-negatives on real content that generic structural mode matches

   File: /home/dl/Documents/code_books.extract/No Starch/bookofkubernetes.md
   Line 5710 (PDF-extraction flattened an entire Python script onto one
   physical line, including inline circled-digit annotations like
   ➊ ➋ ➌ and a one-line `try: ... except: ...`).

   Generic structural mode (no --lang) matches fine:
     agrep -n --structural 'config.load_kube_config(:[args])' \
       './No Starch/bookofkubernetes.md'
     -> matches line 5710, captures args correctly

   Same pattern with --lang py on the identical file/line:
     agrep -n --structural 'config.load_kube_config(:[args])' --lang py \
       './No Starch/bookofkubernetes.md'
     -> zero matches, exit code 1, no error/warning

   Confirmed the literal text is present (agrep -c 'client.CustomObjectsApi()' -> 1),
   and reproduced with a second call in the same line
   (client.CustomObjectsApi(:[args]) also 0 matches under --lang py, matches
   under generic mode).

   This is a silent false negative: --lang py returns a clean "not found"
   result (exit 1, no diagnostic) for text that is demonstrably present and
   that the language-agnostic matcher finds correctly. For an agent
   consuming exit codes / zero-hit results as ground truth, this is worse
   than an error -- it reads as "the pattern isn't in this file." Likely
   trigger: the --lang py parser chokes on the inline circled-digit
   annotation characters and/or the squashed single-line try:/except:
   syntax common in PDF-extracted code samples, and fails closed instead of
   falling back or reporting a parse issue.

3. --block returns low-value results when the triggering match is in a TOC/front-matter section

   agrep --block 'Circuit Breaker' \
     './PragProg/release-it-second-edition_P1.0.md'

   The first match for "Circuit Breaker" falls inside the book's
   "# Table of Contents" section. --block correctly treats the whole
   heading-delimited TOC as the "enclosing block" and returns the entire
   (multi-hundred-line) table of contents rather than anything about
   Circuit Breaker itself. Technically correct per the block-boundary
   definition, but not a useful citation unit -- worth considering whether
   --block should special-case very large/low-density blocks (e.g. flag
   them, or skip pure-listing sections) rather than dumping them whole.

New findings from broad exercise of other flags:

1. --changed-since resolves "is this a git repo" and "what changed"
   against the process's CURRENT WORKING DIRECTORY, not the path(s)
   being searched -- silently wrong scope, not just a missing error.

   Root cause: internal/cli/source.go's gitOutput() runs
   `exec.Command("git", args...)` without setting cmd.Dir, so every
   git call (rev-parse --show-toplevel, diff, ls-files) resolves
   relative to whatever directory agrep's process happens to be
   started in.

   Repro (run from inside this agrep checkout, a git repo, searching
   an unrelated non-git directory):
     cd ~/dev/agrep
     agrep -rn --changed-since main 'Circuit Breaker' \
       ~/Documents/code_books.extract
   -> exit 1, no output, no warning -- looks exactly like "no matches
   for this pattern in this corpus".

   Same command, only cwd changed to something outside any git repo:
     cd /tmp
     agrep -rn --changed-since main 'Circuit Breaker' \
       ~/Documents/code_books.extract
   -> exit 2, "agrep: files-from: --changed-since: not in a git
   repository (...)" -- the documented, honest behavior.

   So whether --changed-since fails loudly or silently returns zero
   depends entirely on an unrelated fact (does $PWD happen to be
   inside *some* git repo), not on whether the searched PATH is a git
   repo. Worse, if $PWD's unrelated repo has real local changes, this
   silently computes "files changed in the wrong repository" and
   filters them against the search path's globs, converging on zero
   survivors -- a silent false negative, the same failure class as
   report bugs 1/2 above ("looks like absence, is actually a tooling
   mismatch"). Fix direction: resolve the git root from the search
   path(s) (paths[0], or each path) rather than os.Getwd()'s implicit
   cwd, and run cmd.Dir set accordingly.

2. Default plain-text output truncates long lines to a fixed 75-byte
   window with no visual indicator that anything was cut -- silently
   indistinguishable from a genuinely short line. (The prior
   evaluation flagged this as untested: "no line long enough in my
   sampling to confirm the truncated:true JSON flag fires... worth a
   dedicated test with a long line." This is that test.)

   Repro:
     sed -n '1762p' PragProg/release-it-second-edition_P1.0.md | wc -c
     # 184 bytes; full text:
     # "A fixed retry interval will concentrate demand from callers on
     #  that period. Instead, use a backoff algorithm so different
     #  callers will be at different points in their backoff periods."
     agrep -n 'backoff' PragProg/release-it-second-edition_P1.0.md
   Line 1762 of the output is exactly 75 bytes:
     1762:on that period. Instead, use a backoff algorithm so different callers
   Both the sentence's start ("A fixed retry interval will concentrate
   demand from callers ") and its end (" will be at different points
   in their backoff periods.") are silently dropped -- no "...", no
   byte count, no marker of any kind, and (unlike --block's "[agrep]
   block truncated at size cap" trailer, internal/output/text.go:219-
   221) the -M column-window path never sets or checks any truncation
   flag for plain-text output. JSON mode is more honest here: without
   an explicit -M, JSON always shows the full line (confirmed: the
   same match's JSON "text" field carries all 184 bytes) and an
   explicit -M sets "truncated":true. Plain-text mode's *default*
   (-M 0 = auto = 75 bytes, internal/cli/run.go:41-42) has no such
   flag at all, applied on every run unless a user knows to pass
   -M -1. Given this project's stated design principle ("the agent
   can no longer tell truncation from absence" -- README.md) this
   same failure applies per-line, by default, in the default output
   mode.

Minor / non-bug observations
-----------------------------
- --structural holes (:[name]) have no distance bound when the
  pattern is applied to prose-heavy, non-source-code corpora: an
  anchor word that also reads as ordinary English ("fn", "func",
  "function", "int") matches inside a book's prose *discussing* that
  keyword, and the hole then lazily consumes everything up to the
  next matching literal -- which can be paragraphs away. Confirmed
  with --structural 'func :[name](:[args]) {' --lang go against
  Alphabet Soup/Computer Science/crafting-interpreters.md: it matched
  the word "func" inside the sentence "I've seen languages that use
  fn, fun, func, and function..." and captured 101 bytes spanning a
  paragraph break (including a blank line) as ":[name]", terminating
  on an unrelated code sample several sentences later. --lang js
  ("function ...") and --lang rs ("fn ...") on the same file landed
  on the exact same code sample via the same mechanism. This is a
  direct, documented consequence of the "no parser, no AST" design
  (structural.go's own header comment), not a contract violation --
  but it's a real precision gap for the --skill-recommended "call
  sites" workflow specifically on natural-language corpora like this
  one, worth a note in the docs (e.g. --structural is code-oriented;
  expect false positives on prose that discusses code keywords).
- Under --max-tokens combined with -l (or -c), the summary's
  shown_lines/omitted_lines fields count 1 per matching/omitted file
  (verified: -l --max-tokens 1 over 43 matching files reported
  shown_files:1/omitted_files:42 and shown_lines:1/omitted_lines:42,
  i.e. lines and files tracked in lockstep). The numbers are
  internally consistent and sum correctly, but the base (non-budget)
  contract documents -l summaries as having no "lines" concept at all
  ({files,errors} only) -- so the field name is a bit of a misnomer
  under -l specifically. Cosmetic; no incorrect totals observed.
- Verified clean, no anomalies found: -r/--outline/--rank
  (count/density/defs), --scope, --ident (cross-case-convention
  matching), --get-region (valid span and the documented exit-2
  out-of-range case), --histogram, --collapse (including combined
  with --max-tokens on a synthetic file forcing >3 duplicate lines --
  true totals and collapsed-count stayed correct, no duplicate JSON
  keys), --suggest (zero-hit text and JSON forms, including the
  suggest_summary-then-summary ordering), -U multiline, -A/-B/-C
  context (plain and JSON parity), -t/-o multi-stage pipelines,
  --with-file/--without-file, -g include/exclude globs, -i/-S/-s case
  handling (including the config-injected smart-case warning firing
  correctly only when the pattern is genuinely all-lowercase),
  --use-index (build, fast reuse, --clear-index), --files-from, and a
  brief --watch invocation (started cleanly, no hang/crash).
